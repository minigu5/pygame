## 0. 이 문서의 역할

기술 설계서는 서버 구조, 프로토콜, 물리, 배포를 다룬다. 이 문서는 **게임 기획**을 다룬다. 맵 구성, 시야, 칠하기 방식, 라운드 규칙이 여기에 속한다.

두 문서가 겹쳤던 항목은 2026-09-21에 합의했다. 결정과 근거는 [9절 합의 결과](#9-합의-결과-2026-09-21)에 있고, 양쪽 문서 모두 그 결정에 맞춰 고쳤다.

## 1. 게임 개요

| 항목 | 내용 |
| --- | --- |
| 프로그램명 | 메챠 카멜레온 2D |
| 설명 | 3D 숨바꼭질 게임 MECCHA CHAMELEON을 2D 횡스크롤(마리오 스타일) 시점으로 다시 만든 게임. 스포이드로 배경색을 찍어 몸을 칠하고 벽과 가구 속에 섞여 숨는다 |
| 장르 | 플랫포머 + 숨바꼭질 (파티 게임) |
| 목표 | 카멜레온은 배경에 맞게 몸을 칠해 5층 건물 속에 숨고, 제한 시간이 끝날 때까지 들키지 않으면 이긴다. 헌터는 방을 하나씩 뒤져 시간 안에 모든 카멜레온을 찾으면 이긴다 |

### 시나리오

도시 한쪽에 오래 방치된 5층 건물 '팔레트 빌딩'이 있다. 층마다 도서관, 미술실, 주방, 창고, 옥탑 다락방처럼 벽지와 가구가 전부 다른 방들이 계단과 문으로 이어져 있다. 이 건물에 사는 카멜레온들이 밤마다 숨바꼭질 대회를 연다.

## 2. 확정된 기획 결정

| 결정 | 이유 |
| --- | --- |
| 시점은 2D 횡스크롤 | 마리오 같은 옆모습 시점 |
| 스포이드를 넣는다 | 없으면 숨는 쪽이 너무 힘들다 |
| 3D의 시점 변화를 대신할 장치(조명 변화, 그림자, 패럴랙스 등)는 넣지 않는다 | 방 단위 시야 제한만으로도 헌터가 찾기 충분히 어렵다 |
| 맵은 5층 건물이고 층은 계단으로 오간다 | 층과 방이 숨는 단위가 된다 |
| 지금 있는 방만 또렷하게 보인다 | 다른 방과 다른 층은 회색으로 죽여 그린다. 구조는 보이되 색은 못 훔친다 |
| 미니맵으로 건물 구조만 보여 준다 | 다른 플레이어 위치는 표시하지 않는다 |
| 칠할 때는 제자리에 고정된다 | 점프 중에 고정하면 공중에 멈춘 채로 칠할 수 있다 |

## 3. 라운드 흐름

| 단계 | 시간(초안) | 카멜레온 | 헌터 |
| --- | --- | --- | --- |
| 숨기 | 60초 | 이동, 고정, 칠하기 | 화면이 가려지고 조작할 수 없음 |
| 찾기 | 120초 | 고정 상태 유지 또는 이동 | 이동, 지목 |
| 결과 | 5초 | 결과 표시 | 결과 표시 |

- 찾기 단계가 끝날 때 한 명이라도 숨어 있으면 카멜레온이 이긴다. 모두 잡히면 헌터가 이긴다.
- 결과 단계가 끝나면 역할을 바꿔 다음 라운드를 진행한다.
- 기술 설계서 MVP에는 라운드 흐름이 없다. 이 절은 7절 M11에서 구현한다.

## 4. 맵: 5층 건물

### 구조

```
 5F  [ 옥탑 다락방 ][계단]
 4F  [ 미술실 ][ 음악실 ][계단]
 3F  [ 도서관 ][ 사무실 ][ 화장실 ][계단]
 2F  [ 침실 ][ 거실 ][계단]
 1F  [ 로비 ][ 주방 ][ 창고 ][계단]
```

- 층마다 방이 1~4개 있다. 방 크기는 한 화면(30×17 타일)에서 가로 두 화면 정도까지로 잡는다.
- 방과 방 사이는 문으로 잇는다. 문은 같은 층에서만 연결된다.
- 계단실은 층마다 같은 x 좌표에 있고 위아래로 이어진다. 계단실도 방 하나로 취급한다.
- 방마다 벽지 무늬와 단색 면적 비율을 다르게 둔다. 단색 방은 칠하기 쉽지만 헌터가 먼저 의심하고, 무늬가 복잡한 방은 칠하기 어렵지만 잘 들키지 않는다.

### 맵 포맷 확장

기술 설계서 4절의 `map_01.json`(`bg`/`solid`/`fg` 레이어, 팔레트 인덱스)을 그대로 쓴다. 여기에 방 정보만 추가한다. 기술 설계서에도 반영했다.

```json
{
  "rooms": [
    {"id": "1F-lobby",   "name": "로비",   "floor": 1, "rect": [0, 40, 30, 8]},
    {"id": "1F-kitchen", "name": "주방",   "floor": 1, "rect": [30, 40, 24, 8]},
    {"id": "1F-stairs",  "name": "계단실", "floor": 1, "rect": [54, 40, 6, 8], "stairs": true}
  ],
  "doors": [
    {"a": "1F-lobby", "b": "1F-kitchen", "tile": [30, 46]}
  ]
}
```

- `rect`는 타일 단위 `[x, y, w, h]`다. 플레이어가 어느 방에 있는지는 몸 중심점이 들어 있는 `rect`로 판정한다.
- 계단은 `solid` 레이어의 경사 발판(한 칸씩 올라가는 계단 타일)으로 만든다. 따로 층 이동 키를 두지 않고 걸어서 오르내린다. 사다리 방식이 필요하면 이후 추가한다.
- Tiled에서는 오브젝트 레이어의 사각형으로 방을 그린다. `tools/tmj_to_map.py`가 이를 `rooms`로 변환한다.
- 방은 카메라 범위이자 스냅샷 필터 단위이므로 **서버도 `rooms`를 읽는다.** RoomDO가 맵을 로드할 때 함께 올린다.

## 5. 시야와 미니맵

### 방 단위 시야

카메라는 플레이어가 아니라 **지금 있는 방**을 기준으로 잡는다. 방 크기가 제각각이므로 배율을 방마다 맞춘다.

- 목표는 방이 **화면 중앙 70%를 채우는 것**이다. `scale = clamp(min(0.7·960/방너비, 0.7·540/방높이), 0.5, 2.0)`
- 배율 하한에 걸릴 만큼 큰 방에서는 카메라가 플레이어를 따라가되 방 `rect` 밖으로 넘어가지 않게 clamp한다
- 방을 옮기면 배율과 위치를 0.2초에 걸쳐 보간한다

방 바깥 영역은 **검게 칠하지 않고 회색으로 죽여서** 그린다.

- 그레이스케일로 바꾸고 밝기를 40%로 낮춘다
- `solid` 타일만 한 단계 밝은 회색으로 그린다. 벽·바닥·계단이 보여 건물 구조를 파악할 수 있다
- `bg` 색은 거의 구분되지 않는다. 다른 방 벽지 색을 미리 훔쳐 칠하는 것을 막는다
- 스포이드는 회색 처리된 영역에서 색을 찍을 수 없다

헌터와 카멜레온 모두 같은 규칙을 따른다. 관전자는 관전 대상의 시야를 따른다.

서버 스냅샷의 `o`(다른 플레이어 목록)는 뷰포트 기준 대신 **같은 방에 있는 플레이어** 기준으로 거른다. 대역폭도 줄고, 다른 방 플레이어 좌표가 클라이언트로 아예 가지 않는다.

### 미니맵

- 화면 오른쪽 위에 건물 단면을 방 단위 사각형으로 그린다. 방 1개는 대략 가로 16~40px, 층 높이는 10px이다.
- 표시하는 것: 내 위치(점), 지금 있는 방(강조), 계단실, 방 이름(M키로 확대했을 때만).
- 헌터 쪽에서는 이미 들어가 본 방을 다른 색으로 칠한다.
- 다른 플레이어 위치는 표시하지 않는다.

## 6. 칠하기

### 고정 모드

- 카멜레온이 `Tab`을 누르면 **고정 모드**에 들어간다. 속도가 0이 되고 중력도 받지 않는다.
- 점프 중에 고정하면 그 높이에 멈춘다. 벽 높은 곳이나 액자 옆에도 숨을 수 있다.
- 고정 중에는 이동과 점프 입력을 무시한다. 다시 `Tab`을 누르면 풀리고, 공중이었다면 떨어진다.
- 고정 상태는 서버가 가진다. `Player`에 `frozen: boolean`을 추가하고, 물리 틱에서 `frozen`이면 위치를 갱신하지 않는다.
- 헌터는 고정 모드를 쓸 수 없다.

### 칠하는 방식

카멜레온의 몸을 **도트 캔버스**로 만든다.

- 몸 크기는 기술 설계서의 24×32px을 유지한다. 이를 2px 칸으로 나눠 12×16칸(192칸) 캔버스로 쓴다.
- 칸마다 RGB 색 하나를 가진다. 처음에는 모든 칸이 기본색이다.
- 칠하기 UI는 고정 모드일 때만 열린다. 화면 옆에 캔버스 확대판(칸당 16px, 192×256px)과 도구창을 띄운다.

| 도구 | 동작 |
| --- | --- |
| 붓 | 1칸, 2×2칸, 4×4칸 |
| 채우기 | 같은 색으로 이어진 칸 전체 |
| 스포이드 | **별도 모드.** `E`로 켜고 끈다. 켜져 있는 동안에만 마우스 왼쪽 클릭이 게임 화면의 배경색을 찍는다 |
| HSB 슬라이더 | 찍은 색을 미세 조정한다 (기술 설계서 `ui_paint.py`) |
| 지우개 | 기본색으로 되돌린다 |
| 되돌리기 | `Ctrl+Z`, 최소 20단계 |

스포이드를 모드로 뺀 이유는 마우스 왼쪽 버튼이 붓과 겹치기 때문이다. 수식키 대신 모드를 쓰면 상태가 눈에 보이고, 색을 여러 번 찍어 비교하기도 쉽다. 모드가 켜져 있으면 커서 모양을 바꾸고 화면 가장자리에 표시를 띄운다.

- 스포이드는 기술 설계서 7절 방식을 따른다. 화면이 아니라 **맵 레이어만 합성한 Surface**에서 색을 읽는다. 방 바깥의 회색 영역에서는 찍히지 않는다.
- 배경을 통째로 복사하는 버튼은 넣지 않는다. 직접 찍고 칠하는 수고가 게임의 재미다.

### 동기화

기술 설계서의 `p` 메시지는 MVP에서 색 하나(`c`)만 담는다. M10에서 도트 캔버스로 가면 캔버스 전체를 담는다.

```json
{"t":"p","g":"8b5e3c8b5e3c...(192칸 × 6자리 hex)"}
```

- 1,152자, 약 1.2KB다. 칠할 때마다 보내지 않고 **고정 모드를 풀 때**와 **숨기 단계가 끝날 때** 한 번씩만 보낸다. 칠하는 동안은 로컬에만 반영한다.
- 수신 요청 과금에는 거의 영향이 없다.

## 7. 개발 단계

기술 설계서 9절의 0~5단계를 먼저 끝낸다. 그다음 아래 단계를 이어서 진행한다.

| 단계 | 내용 | 완료 기준 | 담당 |
| --- | --- | --- | --- |
| 0~5 | 기술 설계서 9절 (접속, 물리, 예측, 단색 도색, 지목, 배포) | 외부에서 접속해 한 판 | |
| M6 | 5층 건물 맵, `rooms`/`doors` 데이터, 계단 | 1층에서 5층까지 걸어서 오르내림 | |
| M7 | 방 단위 카메라와 회색 처리, 방 기준 스냅샷 필터 | 다른 방이 회색으로 죽고 다른 방 플레이어 정보가 오지 않음 | |
| M8 | 미니맵 | 내 위치와 방 구조가 보이고 헌터 방문 기록이 표시됨 | |
| M9 | 고정 모드 | 땅과 공중에서 고정하고 풀 수 있음 | |
| M10 | 도트 캔버스, 도구, 캔버스 동기화 | 무늬를 칠한 몸이 상대 화면에 그대로 보임 | |
| M11 | 라운드 흐름 (숨기, 찾기, 결과, 역할 교대) | 로비 없이 연속으로 여러 판 | |
| M12 | 방 디자인 다양화, 효과음 | 방 10개 이상, 방마다 무늬가 다름 | |

담당 칸은 팀 회의에서 채운다.

## 9. 합의 결과 (2026-09-21)

두 문서가 달랐던 항목을 합의했다. 양쪽 문서 모두 아래 결정에 맞춰 고쳤다.

| # | 항목 | 결정 | 근거 |
| --- | --- | --- | --- |
| 1 | 화면 밖 처리 | 제3안. 방이 화면 중앙 70%를 채우도록 방마다 배율을 맞추고, 방 바깥은 회색으로 죽여 그린다. `solid` 타일만 구분되게 남겨 건물 구조는 보인다 | 검은 화면은 답답하고, 온전히 그리면 은닉이 깨진다. 회색 처리는 구조를 읽게 하면서 벽지 색은 못 훔치게 한다 |
| 2 | 몸 표현 | 이 문서 안. 단, 단계적으로 간다. MVP는 단색, M10에서 12×16칸 도트 캔버스 | 단색 몸은 모든 칸이 같은 색인 캔버스와 같으므로 코드를 버리지 않는다 |
| 3 | 스냅샷 필터 | 이 문서 안. 같은 방 기준 | 은닉 경계가 게임 규칙(방)과 일치하고, 다른 방 좌표가 클라이언트로 아예 가지 않는다 |
| 4 | 맵 구조 | 이 문서 안. 5층 건물, `rooms`/`doors` | 기술 설계서의 "층 쌓기"의 상위 집합이고 훨씬 구체적이다 |
| 5 | 이동 중 도색 | 이 문서 안. 고정 모드에서만 칠한다 | 칠하는 동안 도망칠 수 없다는 점이 기술 설계서가 노리던 긴장을 더 강하게 만든다 |
| 6 | 마우스 왼쪽 버튼 충돌 | 스포이드를 `E`로 켜고 끄는 별도 모드로 뺀다 | 붓과 같은 버튼이라 겹쳤다. 모드는 상태가 눈에 보이고 색을 여러 번 비교하기 좋다 |
| 7 | 서버의 `rooms` 접근 | RoomDO가 맵을 로드할 때 `rooms`도 함께 올린다 | 방 기준 스냅샷 필터를 서버가 하려면 방 경계를 알아야 한다. 기술 설계서에 빠져 있던 항목이다 |

### 함께 정한 것

- **찾기 단계에서 카멜레온은 움직일 수 있다.** 막으면 숨기 단계가 끝난 뒤 120초 동안 할 일이 없다. 움직이면 들킬 위험이 그 대가다
- **방 정원은 MVP에서 2명(1대1)을 유지한다.** 테스트가 쉽다. M11에서 라운드 흐름과 함께 4명으로 넓힌다
- **캔버스 동기화는 hex 1,152자를 그대로 보낸다.** 실제로 무거워지면 그때 압축한다

### 아직 정하지 않은 것

- 숨기 시간과 찾기 시간의 실제 값. 플레이테스트 후 정한다
- 방 그래픽을 단색 스와치 타일만으로 만들지, 무늬 타일을 따로 그릴지
- 7절 담당 칸

## 10. 작업 규칙

- 기능마다 브랜치를 만들고 PR로 main에 합친다. 브랜치 이름은 `feat/<단계>-<내용>` 형식이다 (예: `feat/m7-room-vision`).
- 커밋 메시지는 기존 커밋처럼 `feat:`, `fix:`, `docs:` 접두어를 붙인다.
- 기획을 바꾸면 이 문서를 같은 PR에서 고친다.
