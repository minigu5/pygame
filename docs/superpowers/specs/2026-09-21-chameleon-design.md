# 위장 숨바꼭질 게임 설계 (MECCHA CHAMELEON 클론)

작성일: 2026-09-21
저장소: https://github.com/minigu5/pygame

## 1. 개요

2D 횡스크롤 멀티플레이 숨바꼭질 게임. 카멜레온 역할 플레이어는 자기 몸 색을 배경에 맞춰 칠해 숨고, 헌터 역할 플레이어는 제한된 화면 안에서 카멜레온을 찾아 지목한다.

원작은 2026년 출시된 일본 인디 게임 MECCHA CHAMELEON이다. 원작은 3D 1인칭이지만 이 프로젝트는 2D 횡스크롤로 재해석한다.

### 설계 원칙

**숨는 판정은 서버가 하지 않는다.** 서버는 좌표와 색을 전달할 뿐이고, 위장의 성패는 사람 눈이 판정한다. 배경과 같은 색으로 칠한 플레이어는 화면에 그려져 있어도 보이지 않는다. 가시도 수식이나 시야 차단 계산은 두지 않는다.

이 원칙의 대가로, 클라이언트를 개조하면 화면 안 플레이어의 좌표를 알아낼 수 있다. 친구끼리 노는 규모에서는 문제로 보지 않는다. 나중에 필요해지면 서버 판정을 덧붙일 수 있고, 그때도 프로토콜은 바뀌지 않는다.

## 2. 기술 스택

| 영역 | 선택 | 비고 |
| --- | --- | --- |
| 클라이언트 | Python 3.14 + pygame-ce 2.5.8 | 검증 완료 (SDL 2.32.10) |
| 클라이언트 네트워크 | websockets 17.1 | 별도 스레드에서 수신 |
| 서버 | Cloudflare Workers + Durable Objects (TypeScript) | 상시 가동, 관리 부담 없음 |
| 전송 | WebSocket, JSON 페이로드 | |
| 맵 제작 | Tiled 에디터 + 변환 스크립트 | |
| 배포 | 소유 도메인의 서브도메인 (Cloudflare에 연결됨) | |

### 호스팅을 Workers/DO로 정한 이유

상시 가동 서버가 필요하지만 개인 PC를 계속 켜둘 수 없다. Cloudflare Tunnel은 결국 원본 머신이 켜져 있어야 하므로 제외했다. 무료 VPS(Oracle Always Free 등)는 언어를 Python으로 통일할 수 있지만 OS 관리와 인스턴스 회수 위험이 따른다.

Workers/DO는 방 하나가 Durable Object 인스턴스 하나에 대응해 매칭 요구와 정확히 맞는다. 서버 로직이 TypeScript가 되지만, 클라이언트가 렌더링만 담당하는 구조이므로 양쪽에 중복되는 로직은 사실상 없다.

### 무료 한도 (2026-09 기준)

Workers 무료 플랜은 월 3M 요청과 390K GB-s를 제공한다. WebSocket 수신 메시지는 20:1로 과금되고 송신과 프로토콜 핑은 과금되지 않는다.

**Alarms API를 틱 루프에 쓰면 안 된다.** 알람 호출은 각각 요청으로 과금되므로 30Hz 알람은 월 한도를 약 28시간 만에 소진한다.

대신 `setInterval`을 쓴다. 타이머가 걸려 있으면 DO가 hibernate하지 못해 duration(GB-s)으로 과금되지만, 요청 과금은 발생하지 않는다.

```
첫 플레이어 입장 → setInterval(tick, 16)   // 60Hz
마지막 퇴장      → clearInterval           // hibernate, 과금 0
```

환산 결과:

| 항목 | 계산 | 여유분 |
| --- | --- | --- |
| duration | 390K GB-s ÷ 0.128 GB | 846 방-시간/월 |
| 수신 요청 | 15Hz ÷ 20 = 0.75 req/s/인 | 1111 플레이어-시간/월 |
| 송신 스냅샷 | 과금 없음 | 제한 없음 |
| 스토리지 | DO storage 미사용 | 0 |

DO 스토리지는 사용하지 않는다. 방 상태는 메모리에만 둔다. DO가 축출되면 방이 사라지지만 한 판이 몇 분이므로 허용한다.

## 3. 시스템 구조

```
pygame 클라이언트 (Python)
  입력 수집 → WebSocket 송신
  스냅샷 수신 → 렌더
  게임 판단 로직 없음
        │
        │ wss://<서브도메인>.<도메인>
        ▼
Worker (무상태)
  GET  /rooms       방 목록
  POST /rooms       방 생성, room id 반환
  GET  /ws?room=ID  WebSocket을 해당 DO로 전달
        │
        ▼
RoomDO (방 1개 = 인스턴스 1개)
  플레이어 상태 소유
  60Hz 물리 틱
  20Hz 스냅샷 송신
```

### 저장소 구조

```
pygame/
├─ client/
│  ├─ main.py           게임 루프
│  ├─ net.py            WebSocket 클라이언트
│  ├─ render.py         맵·플레이어 렌더
│  ├─ input.py          키 샘플링과 배칭
│  ├─ predict.py        클라이언트 예측과 보정
│  └─ ui_paint.py       HSB 슬라이더, 스포이트
├─ server/
│  ├─ src/worker.ts     라우팅, 방 목록
│  ├─ src/room.ts       RoomDO, 틱 루프
│  ├─ src/physics.ts    이동과 충돌
│  └─ wrangler.jsonc
├─ shared/
│  ├─ map_01.json       맵 데이터
│  ├─ tuning.json       물리·조작감 상수
│  └─ protocol.md       메시지 스펙
├─ tools/
│  ├─ gen_tileset.py    팔레트 JSON → tileset.png
│  └─ tmj_to_map.py     Tiled .tmj → map_01.json
└─ docs/superpowers/specs/
```

물리 상수는 `shared/tuning.json` 한 곳에 둔다. 서버가 읽고 클라이언트도 예측용으로 같은 값을 읽으므로 두 곳이 어긋나지 않는다. 조작감 조정은 이 파일만 고쳐 재배포한다.

## 4. 맵 포맷

레이어 3겹으로 나눈다.

| 레이어 | 충돌 | 용도 |
| --- | --- | --- |
| `bg` | 없음 | 벽지·타일 등 배경. 위장 대상 |
| `solid` | 있음 | 바닥·벽·발판 |
| `fg` | 없음 | 기둥·난간. 플레이어 앞에 겹쳐 그림 |

타일은 RGB를 직접 담지 않고 팔레트 인덱스를 담는다. 색 정의는 팔레트에 한 번만 둔다.

```json
{
  "tile_size": 32,
  "size": [64, 48],
  "palette": [
    {"name": "empty",  "color": null,           "solid": false},
    {"name": "wood",   "color": [139, 94, 60],  "solid": false},
    {"name": "wall",   "color": [70, 70, 78],   "solid": true},
    {"name": "carpet", "color": [160, 48, 52],  "solid": false}
  ],
  "bg":    [[1,1,1,3,3,...], ...],
  "solid": [[0,0,2,2,0,...], ...],
  "fg":    [[0,0,0,0,0,...], ...],
  "spawn": {"hunter": [96, 320], "chameleon": [1600, 320]}
}
```

64×48 맵의 레이어 한 겹은 3072개 정수로 약 9KB다. 세 겹을 합쳐도 30KB 미만이다.

맵은 가로로만 길면 단조로우므로 층을 쌓고 계단·사다리로 연결한다. 층 구분이 은닉 단위가 된다.

### 맵 제작 흐름

1. `tools/gen_tileset.py`가 팔레트 JSON을 읽어 32×32 단색 스와치를 이어붙인 `tileset.png`를 만든다
2. Tiled에서 그 타일셋으로 `bg`/`solid`/`fg` 레이어를 그린다
3. Tiled에서 `.tmj`로 내보낸다
4. `tools/tmj_to_map.py`가 GID를 팔레트 인덱스로 바꿔 `shared/map_01.json`을 만든다

타일이 단색 스와치이므로 Tiled GID와 팔레트 인덱스가 1:1로 대응한다. 자체 에디터를 만들면 채우기·되돌리기·스크롤을 전부 구현해야 하므로, 맵이 여러 장 필요해지기 전까지는 Tiled를 쓴다.

## 5. 게임 규칙 (MVP)

- 방 정원 2명. 첫 접속자가 헌터, 둘째가 카멜레온
- 카멜레온은 HSB 슬라이더와 스포이트로 몸 색을 바꾼다
- 헌터는 마우스 클릭으로 한 지점을 지목한다. 그 지점 반경 24px 안에 카멜레온이 있으면 잡힌다
- 지목이 빗나가면 3초 쿨다운. 쿨다운이 없으면 화면을 난사해 위장이 무의미해진다
- 잡힌 카멜레온은 헌터 시점 관전 상태가 된다. 조작할 수 없다
- 1대1이므로 잡히면 사실상 판이 끝난다. 다시 놀려면 재접속한다

### MVP에서 제외하는 것

로비와 라운드 흐름, 타운트(휘파람), 클론 생성, 체형·크기·자세 변경, 맵 추가, 관전 시점 전환. 라운드 흐름이 후속 작업 1순위다.

## 6. 렌더링

- 창 960×540, 타일 32px이므로 한 화면에 30×17 타일이 보인다
- 카메라는 플레이어를 중심에 두고 가로·세로 모두 따라간다
- **화면 밖은 검게 칠하지 않는다.** 시야콘도 두지 않는다. 화면에 보이는 영역은 온전히 그린다
- 맵은 매 프레임 타일을 하나씩 그리지 않는다. 레이어별로 큰 Surface에 한 번 그려두고 프레임마다 보이는 부분만 잘라 blit한다. 프레임당 blit 3~4회로 끝난다
- 플레이어는 단색 사각형으로 그린다. 위장이 색으로 이루어지므로 스프라이트 디테일은 오히려 방해가 된다
- `fg` 레이어는 플레이어보다 뒤에 그려 잠깐씩 가려지게 한다

숨는 수단은 세 가지다. 배경 앞에 정지하기, 화면 밖으로 거리 벌리기, 전경 뒤로 들어가기. 움직이면 색이 같아도 윤곽이 흔들려 눈에 띈다.

## 7. 프로토콜

전송은 WebSocket, 페이로드는 JSON이다. 필드명은 1~2글자로 줄여 수신 요청당 바이트를 아낀다. 전체 스펙은 `shared/protocol.md`에 둔다.

### 서버가 소유하는 상태

```ts
type Player = {
  id: string
  role: "hunter" | "chameleon" | "spectator"
  x: number; y: number
  vx: number; vy: number
  onGround: boolean
  color: [number, number, number]
  caught: boolean
}
```

방 전체는 `Map<id, Player>`와 맵 참조, 틱 카운터로 이루어진다. 전부 메모리에 둔다.

### 클라이언트 → 서버

**`i` (input)** — 15Hz 송신, 4프레임 배칭

```json
{"t":"i","n":128,"k":[4,4,5,5]}
```

`n`은 입력 시퀀스 번호이고 `k`는 프레임별 키 비트마스크 배열이다(1=좌, 2=우, 4=점프). 클라이언트는 60Hz로 입력을 샘플링해 4프레임을 모아 한 번 보내고, 서버는 이를 순서대로 4틱에 나눠 적용한다. 요청 수를 15Hz로 유지하면서 프레임 단위 정밀도를 보존한다.

**`p` (paint)** — 색이 바뀔 때만

```json
{"t":"p","c":[139,94,60]}
```

스포이트는 서버 기능이 아니다. 클라이언트가 마우스 위치의 픽셀 색을 읽어 이 메시지로 보낸다. 픽셀은 맵 레이어만 합성한 Surface에서 읽는다. 화면에서 직접 읽으면 다른 플레이어나 UI 색이 섞인다.

**`a` (accuse)** — 헌터의 지목

```json
{"t":"a","x":512,"y":288}
```

### 서버 → 클라이언트

**`s` (snapshot)** — 20Hz

```json
{"t":"s","n":128,
 "me":{"x":320,"y":416,"vy":-120,"c":[139,94,60]},
 "o":[{"i":"a3","x":512,"y":288,"c":[70,70,78]}]}
```

`n`은 서버가 마지막으로 처리한 내 입력 번호다. `o`는 내 뷰포트 안에 있는 다른 플레이어다. 뷰포트 컬링은 대역폭 절약이 목적이며 은닉 장치가 아니다.

관전자에게는 관전 대상 헌터와 같은 뷰포트 기준으로 스냅샷을 보낸다.

**`j` (join)**, **`c` (caught)**, **`b` (bye)** — 상태 변화 알림.

## 8. 물리

### 틱 구성

duration 과금은 벽시계 시간 기준이므로 틱을 빨리 돌려도 비용이 늘지 않는다. 송신도 과금되지 않는다. 과금되는 것은 수신 메시지 수뿐이다.

| 항목 | 주기 |
| --- | --- |
| 서버 물리 틱 | 60Hz (16.6ms) |
| 서버 → 클라 스냅샷 | 20Hz |
| 클라 → 서버 입력 | 15Hz (4프레임 배칭) |

### 초기 상수

값은 전부 `shared/tuning.json`에 둔다. 실제로 플레이해 보기 전에는 조작감을 판단할 수 없으므로 아래는 출발점일 뿐이며, 구현 후 조정한다.

```
중력           2000 px/s²
이동 속도       200 px/s
점프 초속도     -620 px/s    (최고점 96px = 3타일)
종단 낙하 속도   900 px/s
플레이어 크기    24 × 32 px
코요테 타임      100 ms
점프 버퍼        120 ms
가변 점프        키를 일찍 떼면 상승 속도 절반
```

### 충돌

축 분리 방식을 쓴다. X축으로 이동한 뒤 겹친 solid 타일로 밀어내고, 그다음 Y축으로 같은 처리를 한다. 모서리 끼임이 생기지 않고 구현이 짧다.

### 클라이언트 예측과 보정

- 내 캐릭터는 입력 즉시 로컬에서 물리를 적용한다. 스냅샷의 `n`을 받으면 그 시점 상태로 되돌리고 이후 입력을 재실행한다
- 오차가 8px 미만이면 무시하고, 그 이상이면 3프레임에 걸쳐 당긴다. 순간이동을 막는다
- 다른 캐릭터는 스냅샷 두 개 사이를 보간해 그린다. 50ms 지연 렌더가 된다

## 10. 배포

클라이언트는 Python과 pygame-ce를 직접 설치해 실행한다. README에 설치 절차를 적고 `requirements.txt`를 둔다. PyInstaller 묶음은 후속으로 미룬다.

서버는 `wrangler deploy`로 배포하고, 이미 Cloudflare에 연결된 도메인의 서브도메인 하나를 Worker에 붙인다. 로컬 개발은 `wrangler dev`로 하며 4단계까지는 배포 없이 진행할 수 있다.
