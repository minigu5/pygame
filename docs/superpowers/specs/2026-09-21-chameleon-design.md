# 위장 숨바꼭질 게임 설계 (MECCHA CHAMELEON 클론)

작성일: 2026-09-21
최종 수정: 2026-09-21 (기획 스펙과 합의 반영)
저장소: https://github.com/minigu5/pygame
관련 문서: [메챠 카멜레온 2D 게임 기획 스펙](2026-09-21-meccha-chameleon-2d-game-spec.md) (이하 **기획 스펙**)

이 문서는 서버 구조, 프로토콜, 물리, 배포를 다룬다. 맵 구성, 시야, 칠하기 방식, 라운드 규칙은 기획 스펙에 있다.

## 1. 개요

2D 횡스크롤 멀티플레이 숨바꼭질 게임. 카멜레온 역할 플레이어는 자기 몸 색을 배경에 맞춰 칠해 숨고, 헌터 역할 플레이어는 제한된 화면 안에서 카멜레온을 찾아 지목한다.

원작은 2026년 출시된 일본 인디 게임 MECCHA CHAMELEON이다. 원작은 3D 1인칭이지만 이 프로젝트는 2D 횡스크롤로 재해석한다.

### 설계 원칙

**숨는 판정은 서버가 하지 않는다.** 서버는 좌표와 색을 전달할 뿐이고, 위장의 성패는 사람 눈이 판정한다. 배경과 같은 색으로 칠한 플레이어는 화면에 그려져 있어도 보이지 않는다. 가시도 수식이나 시야 차단 계산은 두지 않는다.

이 원칙의 대가로, 클라이언트를 개조하면 **같은 방에 있는** 플레이어의 좌표를 알아낼 수 있다. 다른 방 플레이어는 서버가 보내지 않으므로 알아낼 수 없다. 친구끼리 노는 규모에서는 문제로 보지 않는다. 나중에 필요해지면 서버 판정을 덧붙일 수 있고, 그때도 프로토콜은 바뀌지 않는다.

## 2. 기술 스택

| 영역 | 선택 | 비고 |
| --- | --- | --- |
| 클라이언트 | Python 3.14 + pygame-ce 2.5.8 | 검증 완료 (SDL 2.32.10) |
| 클라이언트 네트워크 | websockets 17.1 | 별도 스레드에서 수신 |
| 서버 | Cloudflare Workers + Durable Objects (TypeScript) | 상시 가동, 관리 부담 없음 |
| 전송 | WebSocket, JSON 페이로드 | |
| 맵 제작 | Tiled 에디터 + 변환 스크립트 | |
| 배포 | 소유 도메인의 서브도메인 (Cloudflare에 연결됨) | |

### 호스팅을 Workers/DO로 정한 이유

상시 가동 서버가 필요하지만 개인 PC를 계속 켜둘 수 없다. Cloudflare Tunnel은 결국 원본 머신이 켜져 있어야 하므로 제외했다. 무료 VPS(Oracle Always Free 등)는 언어를 Python으로 통일할 수 있지만 OS 관리와 인스턴스 회수 위험이 따른다.

Workers/DO는 방 하나가 Durable Object 인스턴스 하나에 대응해 매칭 요구와 정확히 맞는다. 서버 로직이 TypeScript가 되지만, 클라이언트가 렌더링만 담당하는 구조이므로 양쪽에 중복되는 로직은 사실상 없다.

### 무료 한도 (2026-09 기준)

Workers 무료 플랜은 월 3M 요청과 390K GB-s를 제공한다. WebSocket 수신 메시지는 20:1로 과금되고 송신과 프로토콜 핑은 과금되지 않는다.

**Alarms API를 틱 루프에 쓰면 안 된다.** 알람 호출은 각각 요청으로 과금되므로 30Hz 알람은 월 한도를 약 28시간 만에 소진한다.

대신 `setInterval`을 쓴다. 타이머가 걸려 있으면 DO가 hibernate하지 못해 duration(GB-s)으로 과금되지만, 요청 과금은 발생하지 않는다.

```
첫 플레이어 입장 → setInterval(tick, 16)   // 60Hz
마지막 퇴장      → clearInterval           // hibernate, 과금 0
```

환산 결과:

| 항목 | 계산 | 여유분 |
| --- | --- | --- |
| duration | 390K GB-s ÷ 0.128 GB | 846 방-시간/월 |
| 수신 요청 | 15Hz ÷ 20 = 0.75 req/s/인 | 1111 플레이어-시간/월 |
| 송신 스냅샷 | 과금 없음 | 제한 없음 |
| 스토리지 | DO storage 미사용 | 0 |

DO 스토리지는 사용하지 않는다. 방 상태는 메모리에만 둔다. DO가 축출되면 방이 사라지지만 한 판이 몇 분이므로 허용한다.

## 3. 시스템 구조

```
pygame 클라이언트 (Python)
  입력 수집 → WebSocket 송신
  스냅샷 수신 → 렌더
  게임 판단 로직 없음
        │
        │ wss://<서브도메인>.<도메인>
        ▼
Worker (무상태)
  GET  /rooms       방 목록
  POST /rooms       방 생성, room id 반환
  GET  /ws?room=ID  WebSocket을 해당 DO로 전달
        │
        ▼
RoomDO (방 1개 = 인스턴스 1개)
  플레이어 상태 소유
  60Hz 물리 틱
  20Hz 스냅샷 송신
```

├─ server/
│  ├─ src/worker.ts     라우팅, 방 목록

## 4. 맵 포맷

레이어 3겹으로 나눈다.

| 레이어 | 충돌 | 용도 |
| --- | --- | --- |
| `bg` | 없음 | 벽지·타일 등 배경. 위장 대상 |
| `solid` | 있음 | 바닥·벽·발판 |
| `fg` | 없음 | 기둥·난간. 플레이어 앞에 겹쳐 그림 |

타일은 RGB를 직접 담지 않고 팔레트 인덱스를 담는다. 색 정의는 팔레트에 한 번만 둔다.

```json
{
  "tile_size": 32,
  "size": [64, 48],
  "palette": [
    {"name": "empty",  "color": null,           "solid": false},
    {"name": "wood",   "color": [139, 94, 60],  "solid": false},
    {"name": "wall",   "color": [70, 70, 78],   "solid": true},
    {"name": "carpet", "color": [160, 48, 52],  "solid": false}
  ],
  "bg":    [[1,1,1,3,3,...], ...],
  "solid": [[0,0,2,2,0,...], ...],
  "fg":    [[0,0,0,0,0,...], ...],
  "rooms": [
    {"id": "1F-lobby",   "name": "로비",   "floor": 1, "rect": [0, 40, 30, 8]},
    {"id": "1F-kitchen", "name": "주방",   "floor": 1, "rect": [30, 40, 24, 8]},
    {"id": "1F-stairs",  "name": "계단실", "floor": 1, "rect": [54, 40, 6, 8], "stairs": true}
  ],
  "doors": [
    {"a": "1F-lobby", "b": "1F-kitchen", "tile": [30, 46]}
  ],
  "spawn": {"hunter": [96, 320], "chameleon": [1600, 320]}
}
```

64×48 맵의 레이어 한 겹은 3072개 정수로 약 9KB다. 세 겹을 합쳐도 30KB 미만이다.

### 방 구조

맵은 5층 건물이다. 층마다 방이 1~4개 있고 계단실로 위아래를 잇는다. 구성은 기획 스펙 4절에 있다.

`rooms[].rect`는 타일 단위 `[x, y, w, h]`다. 플레이어가 어느 방에 있는지는 몸 중심점이 들어 있는 `rect`로 판정한다. 방은 카메라 범위이자 스냅샷 필터 단위이므로, **서버도 `rooms`를 읽어야 한다.** RoomDO가 맵을 로드할 때 `rooms`를 함께 올린다.

계단은 `solid` 레이어의 경사 발판으로 만든다. 층 이동 전용 키는 두지 않고 걸어서 오르내린다.

### 맵 제작 흐름

1. `tools/gen_tileset.py`가 팔레트 JSON을 읽어 32×32 단색 스와치를 이어붙인 `tileset.png`를 만든다
2. Tiled에서 그 타일셋으로 `bg`/`solid`/`fg` 레이어를 그린다
3. 오브젝트 레이어에 방을 사각형으로 그리고 이름과 층을 속성으로 넣는다
4. Tiled에서 `.tmj`로 내보낸다
5. `tools/tmj_to_map.py`가 GID를 팔레트 인덱스로, 오브젝트 사각형을 `rooms`로 바꿔 `shared/map_01.json`을 만든다

타일이 단색 스와치이므로 Tiled GID와 팔레트 인덱스가 1:1로 대응한다. 자체 에디터를 만들면 채우기·되돌리기·스크롤을 전부 구현해야 하므로, 맵이 여러 장 필요해지기 전까지는 Tiled를 쓴다.

## 5. 게임 규칙 (MVP)

- 방 정원 2명. 첫 접속자가 헌터, 둘째가 카멜레온
- 카멜레온은 `Tab`으로 **고정 모드**에 들어가야 칠할 수 있다. 고정 중에는 속도가 0이고 중력도 받지 않아 공중에서도 멈춘다. 칠하는 동안 도망칠 수 없다는 점이 긴장을 만든다
- 색은 스포이드와 HSB 슬라이더로 정한다. 스포이드는 **별도 모드**이며, 그 모드에서만 마우스 왼쪽 클릭이 색을 찍는다
- 헌터는 마우스 클릭으로 한 지점을 지목한다. 그 지점 반경 24px 안에 카멜레온이 있으면 잡힌다
- 지목이 빗나가면 3초 쿨다운. 쿨다운이 없으면 화면을 난사해 위장이 무의미해진다
- 잡힌 카멜레온은 헌터 시점 관전 상태가 된다. 조작할 수 없다
- 1대1이므로 잡히면 사실상 판이 끝난다. 다시 놀려면 재접속한다

### MVP에서 제외하는 것

로비와 라운드 흐름, 타운트(휘파람), 클론 생성, 체형·크기·자세 변경, 맵 추가, 관전 시점 전환, 도트 캔버스(MVP는 몸 전체가 단색).

MVP 다음 작업은 기획 스펙 7절의 M6~M12를 따른다. 라운드 흐름은 M11이다.

## 6. 렌더링

창은 960×540이고 타일은 32px이다. 기본 배율에서 한 화면에 30×17 타일이 보인다.

### 방 단위 카메라

카메라는 플레이어가 아니라 **지금 있는 방**을 기준으로 잡는다. 목표는 방이 화면 중앙의 70% 영역을 채우는 것이다.

```
scale = min(0.7 · 960 / 방_너비_px, 0.7 · 540 / 방_높이_px)
scale = clamp(scale, 0.5, 2.0)
```

- 방이 작으면 확대되고, 크면 축소된다. 방마다 배율이 달라도 방 전체가 한눈에 들어온다
- `scale`이 하한 0.5에 걸릴 만큼 큰 방에서는 방 전체를 담기를 포기하고, 카메라가 플레이어를 따라가되 방 `rect` 밖으로 넘어가지 않게 clamp한다
- 방을 옮기면 배율과 위치를 0.2초에 걸쳐 보간한다. 튀지 않는다

### 방 바깥 표현

방 바깥 30% 영역은 **검게 칠하지 않는다.** 회색으로 죽여서 그린다.

- 바깥 영역은 그레이스케일로 변환하고 밝기를 40%로 낮춘다
- `solid` 타일은 바깥에서도 한 단계 밝은 회색으로 그린다. 건물 구조(벽, 바닥, 계단 위치)는 파악할 수 있다
- `bg` 색은 거의 구분되지 않는다. 다른 방의 벽지 색을 훔쳐 미리 칠하는 것을 막는다
- **다른 방 플레이어는 그릴 수 없다.** 서버가 좌표를 보내지 않기 때문이다

### 그리기

- 맵은 매 프레임 타일을 하나씩 그리지 않는다. 레이어별로 큰 Surface에 한 번 그려두고 프레임마다 보이는 부분만 잘라 blit한다. 회색 버전도 같은 방식으로 한 번 만들어 둔다
- 플레이어는 MVP에서 단색 사각형으로 그린다. M10에서 12×16칸 도트 캔버스로 넓힌다. 단색은 모든 칸이 같은 색인 캔버스와 같으므로 코드를 버리지 않는다
- `fg` 레이어는 플레이어보다 앞에 그려 잠깐씩 가려지게 한다

숨는 수단은 세 가지다. 배경 앞에 고정하기, 다른 방으로 옮기기, 전경 뒤로 들어가기. 움직이면 색이 같아도 윤곽이 흔들려 눈에 띈다.

## 7. 프로토콜

전송은 WebSocket, 페이로드는 JSON이다. 필드명은 1~2글자로 줄여 수신 요청당 바이트를 아낀다. 전체 스펙은 `shared/protocol.md`에 둔다.

### 서버가 소유하는 상태

```ts
type Player = {
  id: string
  role: "hunter" | "chameleon" | "spectator"
  x: number; y: number
  vx: number; vy: number
  onGround: boolean
  frozen: boolean            // 고정 모드. true면 물리 틱이 위치를 갱신하지 않음
  room: string               // 지금 있는 방 id. 매 틱 갱신
  color: [number, number, number]
  caught: boolean
}
```

방 전체는 `Map<id, Player>`와 맵 참조, 틱 카운터로 이루어진다. 전부 메모리에 둔다.

### 클라이언트 → 서버

**`i` (input)** — 15Hz 송신, 4프레임 배칭

```json
{"t":"i","n":128,"k":[4,4,5,5]}
```

`n`은 입력 시퀀스 번호이고 `k`는 프레임별 키 비트마스크 배열이다(1=좌, 2=우, 4=점프). 클라이언트는 60Hz로 입력을 샘플링해 4프레임을 모아 한 번 보내고, 서버는 이를 순서대로 4틱에 나눠 적용한다. 요청 수를 15Hz로 유지하면서 프레임 단위 정밀도를 보존한다.

**`f` (freeze)** — 고정 모드 토글

```json
{"t":"f","v":true}
```

고정 상태는 서버가 가진다. `frozen`이면 물리 틱에서 위치를 갱신하지 않으므로 공중에서도 멈춘다. 풀면 그 자리에서 다시 중력을 받는다. 헌터는 이 메시지를 보낼 수 없다.

**`p` (paint)** — 색이 바뀔 때만

```json
{"t":"p","c":[139,94,60]}
```

스포이드는 서버 기능이 아니다. 클라이언트가 마우스 위치의 픽셀 색을 읽어 이 메시지로 보낸다. 픽셀은 맵 레이어만 합성한 Surface에서 읽는다. 화면에서 직접 읽으면 다른 플레이어나 UI 색이 섞인다. 방 바깥의 회색 처리된 영역에서는 색을 찍을 수 없다.

M10에서 도트 캔버스로 넓히면 이 메시지가 캔버스 전체(192칸)를 담는다. 형식은 기획 스펙 6절에 있다. 칠하는 동안에는 보내지 않고 고정 모드를 풀 때 한 번 보낸다.

**`a` (accuse)** — 헌터의 지목

```json
{"t":"a","x":512,"y":288}
```

### 서버 → 클라이언트

**`s` (snapshot)** — 20Hz

```json
{"t":"s","n":128,
 "me":{"x":320,"y":416,"vy":-120,"fz":false,"rm":"1F-lobby","c":[139,94,60]},
 "o":[{"i":"a3","x":512,"y":288,"fz":true,"c":[70,70,78]}]}
```

`n`은 서버가 마지막으로 처리한 내 입력 번호다. `rm`은 내가 있는 방 id이고 클라이언트는 이 값으로 카메라를 잡는다.

`o`는 **나와 같은 방에 있는** 다른 플레이어다. 뷰포트 기준이 아니라 방 기준으로 거른다. 방이 게임 규칙상의 은닉 단위와 일치하고, 다른 방 플레이어의 좌표가 클라이언트로 아예 가지 않는다.

관전자에게는 관전 대상 헌터가 있는 방을 기준으로 스냅샷을 보낸다.

**`j` (join)**, **`c` (caught)**, **`b` (bye)** — 상태 변화 알림.

## 8. 물리

### 틱 구성

duration 과금은 벽시계 시간 기준이므로 틱을 빨리 돌려도 비용이 늘지 않는다. 송신도 과금되지 않는다. 과금되는 것은 수신 메시지 수뿐이다.

| 항목 | 주기 |
| --- | --- |
| 서버 물리 틱 | 60Hz (16.6ms) |
| 서버 → 클라 스냅샷 | 20Hz |
| 클라 → 서버 입력 | 15Hz (4프레임 배칭) |

### 초기 상수

값은 전부 `shared/tuning.json`에 둔다. 실제로 플레이해 보기 전에는 조작감을 판단할 수 없으므로 아래는 출발점일 뿐이며, 구현 후 조정한다.

```
중력           2000 px/s²
이동 속도       200 px/s
점프 초속도     -620 px/s    (최고점 96px = 3타일)
종단 낙하 속도   900 px/s
플레이어 크기    24 × 32 px
코요테 타임      100 ms
점프 버퍼        120 ms
가변 점프        키를 일찍 떼면 상승 속도 절반
```

### 충돌

축 분리 방식을 쓴다. X축으로 이동한 뒤 겹친 solid 타일로 밀어내고, 그다음 Y축으로 같은 처리를 한다. 모서리 끼임이 생기지 않고 구현이 짧다.

### 클라이언트 예측과 보정

- 내 캐릭터는 입력 즉시 로컬에서 물리를 적용한다. 스냅샷의 `n`을 받으면 그 시점 상태로 되돌리고 이후 입력을 재실행한다
- 오차가 8px 미만이면 무시하고, 그 이상이면 3프레임에 걸쳐 당긴다. 순간이동을 막는다
- 다른 캐릭터는 스냅샷 두 개 사이를 보간해 그린다. 50ms 지연 렌더가 된다

## 9. 개발 단계

| 단계 | 내용 | 완료 기준 |
| --- | --- | --- |
| 0 | 저장소 뼈대, `map_01.json`, `wrangler dev` + Python 클라 연결 | ping/pong 왕복 |
| 1 | 서버 물리·충돌, 클라는 받은 좌표만 그림 | 두 창에서 서로 움직임이 보임 |
| 2 | 클라이언트 예측과 보간 | 내 캐릭터가 지연 없이 움직임 |
| 3 | 고정 모드, 스포이드 모드, HSB 슬라이더, 단색 도색 동기화 | 색이 바뀌고 상대 화면에 반영됨 |
| 4 | 방 단위 카메라와 스냅샷 필터, 지목과 잡기, 관전 | 게임이 성립함 |
| 5 | 서브도메인 연결, 배포 | 외부에서 접속해 한 판 |

이후 단계(M6~M12)는 기획 스펙 7절에 있다. 5층 건물 맵은 M6에서 완성하므로, 0~4단계에서는 방 2~3개짜리 시험용 맵을 쓴다.

## 10. 배포

클라이언트는 Python과 pygame-ce를 직접 설치해 실행한다. README에 설치 절차를 적고 `requirements.txt`를 둔다. PyInstaller 묶음은 후속으로 미룬다.

서버는 `wrangler deploy`로 배포하고, 이미 Cloudflare에 연결된 도메인의 서브도메인 하나를 Worker에 붙인다. 로컬 개발은 `wrangler dev`로 하며 4단계까지는 배포 없이 진행할 수 있다.
